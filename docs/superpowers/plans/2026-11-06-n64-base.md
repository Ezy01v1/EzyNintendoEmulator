# Nintendo 64 Base (Subproject 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A new `ezy_n64` core that runs N64 programs on an interpreted VR4300 (with COP0/TLB and COP1), boots through the cartridge's real IPL3 after an HLE PIF boot, and shows the VI framebuffer. PeterLemon's CPU test ROMs and the non-RSP/RDP parts of n64-systemtest must pass.

**Architecture:** The same shape as `src/core/gba`. The CPU (`cpu/vr4300`) executes one instruction per `step()` and returns the cycles it took. It talks to memory only through the `CpuBus` interface, with physical addresses, so tests use a flat bus. `Bus` maps physical addresses to RDRAM, the RCP interfaces (MI, PI, SI, VI, AI, SP/DP stubs, RI), the cartridge and the PIF. Devices with timing (VI lines, PI/SI/AI DMA) use an event `Scheduler` counted in CPU cycles. `N64` owns everything and runs the step/dispatch loop.

**Tech Stack:** C++20, CMake presets (`build/default`), doctest, SDL3 + Dear ImGui frontend, PeterLemon/N64 test ROMs, n64-systemtest (built with Rust nightly).

**Spec:** `docs/superpowers/specs/2026-11-06-n64-base-design.md`

## Global Constraints

- Build with the presets (`cmake --build --preset release` / `debug`); ROM tests run with `ctest --test-dir build/default -C Release`. On the Build Tools PC, `cmake` is in `C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin`.
- English code, comments and commits; commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Style of `src/core/gba`: C++20, `[[nodiscard]]`, `std::span`, comments that explain the hardware. Namespace `ezy::n64`.
- Branch `n64/base`, one commit per piece of hardware, PR to `main` at the end.
- CPU clock: **93,750,000 Hz**. `Count` advances once every **2** CPU cycles.
- Extra cycles: `MULT/MULTU` +5, `DMULT/DMULTU` +8, `DIV/DIVU` +37, `DDIV/DDIVU` +69, FPU ops per the VR4300 manual table. Uncached accesses add a fixed penalty per destination (named constants, each with a comment). Cached accesses add nothing.
- Cache contents are not emulated; `CACHE` is a no-op.
- RDRAM is 8 MB. Everything is big-endian.
- HLE boot runs the cartridge's real IPL3; never copy the game into RDRAM ourselves. Optional real PIF ROM boots from `0xBFC00000`.
- Unmapped physical reads return 0, writes are dropped (debug log), unless n64-systemtest expects otherwise. Reserved instructions raise the Reserved Instruction exception.
- If a program starts the RSP or sends RDP commands: log once, ignore, RSP stays halted.
- Screenshots are compared on the native VI image, never on the 640×480 canvas.
- ROMs, PIF ROM and n64-systemtest binaries are never committed (`roms/` is ignored).
- No regressions in the existing ctest (GB, GBA, CHIP-8).

## Review Focus

1. **An exception in a branch delay slot** must set `Cause.BD` and `EPC` to the branch, and `ERET` must resume at the branch. Every test ROM with traps or TLB misses depends on it. Test in Task 3: `"exception in a delay slot sets BD and EPC to the branch"`.
2. **32-bit results must be sign-extended to 64 bits** (`ADDU`, `LW`, `SLL`, `MFC0`, …), and 64-bit ops must be Reserved Instruction in 32-bit user/supervisor mode. A missed sign extension breaks every kseg0 pointer. Tests in Task 2: `"32-bit ops sign-extend"`, and Task 3: `"64-bit op in 32-bit user mode is reserved"`.
3. **A ROM with a byte order or size we don't expect** (`.v64` byte-swapped, `.n64` little-endian, odd sizes, less than 4 KB) must load correctly or be refused, never crash. Test in Task 1: `"rom smaller than the header and IPL3 is refused"`.
4. **PI DMA with odd addresses or lengths** (unaligned RDRAM address, odd length) must follow the hardware's alignment rules, which PeterLemon's `DMAAlignment-PI-cart` measures. Test in Task 6: `"PI DMA aligns the RDRAM address down to 8 bytes"`.
5. **A save state taken while a PI or AI DMA is pending** must resume it and finish at the same cycle. Test in Task 10: `"save state mid-DMA resumes at the same cycle"`.
